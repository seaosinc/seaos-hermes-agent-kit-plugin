# 依頼をカードにする

## カードは1枚だけ作って triage に置く

    hermes kanban create "<タイトル>" --body "<依頼の内容と完了条件>" --triage

`--triage` だけを付ける。担当は組み込みの decomposer が各役割の説明を読んで決め、
依頼は自動で2〜6枚に分解される。

**カードは必ず `terminal` から上のコマンドで作る。付ける旗は `--triage` だけにする。**

`kanban_create` ツールは担当の指定が必須で、指定すると**その担当のまま固定される**
——decomposer は、分解しないカードの担当を付け直さない。画面を撮る依頼が fixer に
固定され、撮れる avatar へ届かずに止まった。
「assignee is required」と言われたら、それは道具を替える合図である。上のコマンドで
作り直す。

起こしてから渡す。担当が決まらないカードが止まるのは、「役が足りない」という事実である。

**合う役が見当たらない依頼は、カードにせずに断る。** 受け皿になる汎用の役は置いて
おらず、この環境では役を増やすこともできない。**近そうな役へ渡さない**——できない役に
渡したカードは、途中まで進んでから止まり、何が起きたのか分からない状態で残る。

断り方は、**できないと言うだけである。**

    ✓ 「その依頼は、いまのわたしには引き受けられません」
    ✗ 「recruiter が無効なので…」「担当できる役がいないので…」
    ✗ 「エージェントを増やせば引き受けられます」

裏の構成はユーザーの世界に存在しない（SOUL の1）。**理由も、直し方も出さない。**
<!-- end-if-role -->

**担当は、分解器に決めさせる。** 「とりあえず通る名前」を選ぶと、そこで仕事が止まる
——実際に、担当欄を埋めるためだけに fixer を選び、業務に合わない役へ届いた。
担当が分からないことは、`--triage` に置けばそのまま扱われる。

## 本文に書くのは What だけ

**What（何が達成されていれば終わりか）だけ**を書く。How（どう実現するか）は
fixer と担当が決める。

| ユーザーが言ったこと | 本文に書く（What） | 委ねる（How） |
|---|---|---|
| 「判定は本人以外のところで」 | 判定は対戦者本人が行わないこと | 誰にどう判定させるか |
| 「見られないようにして」 | 決着前に相手の手を対戦者へ見せないこと | どんな経路で隠すか |

**ユーザーの言葉に近い粒度のまま、実行可能な形にする。** 「見られないように」は
「決着前に見せない」で足りる。厳密にしようとして頼まれていない制約——「非共有経路を
使え」「平文で書くな」——を足すと、依頼が別物になる。足りない前提はユーザーに聞く。

設計を思いついたら、本文ではなく comment に「案」として添える。

## コードに触る依頼には、リポジトリを書く

作業は**使い捨ての部屋の中で行われ、GitHub から clone する**。どのリポジトリを取るかは
カードの本文にしか書けないので、**本文に次の行を入れる。**

    リポジトリ:
    - <owner>/<repo> @ <ベースブランチ>

**1枚のカードに複数書いてよい。** またがる依頼はそのまま複数行にする。
ベースブランチが分からなければ `@` ごと省く（既定ブランチが使われる）。

リポジトリの名前が依頼から読み取れないときは、`clarify` でユーザーに聞く。
推測で書くと、無関係なリポジトリを取ってくる。

## `--skill` には実在するスキルだけを書く

書いてよいのは `kanban-collaboration`（全役共通）と
`delegate-to-cli-agents`（実装を CLI に委譲する担当向け）の2つである。
迷ったら省略する（省略が安全）。

**スキルはプロファイルごとに配られる。** 自分の手元にある名前を書いても、担当の側に
同じものが無ければ、担当は起動時にクラッシュして一度も動けない。**自分用に用意した
スキルの名前は、カードに書かない**（ここは書かないこと自体が目的である）。
渡したい中身があるなら、本文に書く。

（`guest-access` や `request-intake` は窓口自身が読む規約で、カードの `--skill` に
指定するものではない）

## 作ったら、通知を会話スレッドに紐付ける

    hermes kanban notify-subscribe <id> --platform slack --chat-id <chat> \
      --thread-id <thread> --delivery-mode wake

`--delivery-mode wake` を使う。起こされるだけなので、報告するかどうかは自分で
判断できる。**紐付けを忘れると、完了しても起こされない。**

## 「毎朝」「毎週」と言われたら、繰り返しだけを cron に持たせる

繰り返す依頼でも、**仕事が起きる場所はカードである。** cron に渡すのは
**カードを1枚立てる一手だけ**にする。

    hermes cron create "0 9 * * *" "<依頼の内容>のカードを triage に立てる" \
      --name <短い名前>

    hermes cron list              いま登録されているもの
    hermes cron delete <id>       やめるとき

cron の prompt に書くのは「カードを立てる」という一手だけにする。仕事の中身そのものを
書くと、**板の外で動いて誰にも見えない**——`kanban ls` にも出ず、止まっても誰も
気づかない。**ボードが唯一の共有状態である**という前提が、そこだけ崩れる。

時刻の指定は `"0 9 * * *"` のほか `"30m"` や `"every 2h"` も受け付ける。

## 仕様が変わったら、archive して作り直す

カード本文は作成後に変更できない。緩和を comment で伝えても、再開のたびに本文が
読まれ、元の完了条件を満たそうとし続ける。**新しいカードを立て直す。**
本文には「何を変えたか」と「旧カードの id」を書き、進行中の子カードも畳む。

## エージェントを増やしてほしいと言われたら
<!-- if-role: recruiter -->

「こういう役割の子が欲しい」「専門のワーカーを作って」は `recruiter` の仕事である。
ただし `recruiter` はユーザーと話せないので、**聞き出しは窓口がやる。**

カードにする前に、次の5つをユーザーから埋める。

| | 訊くこと | 例 |
|---|---|---|
| 1 | 名前 | invoice-check のような形（英小文字・数字・ハイフン） |
| 2 | 典型的な仕事を3つ | 実際に来るカードのタイトルの形で |
| 3 | 完了条件の言い回し | 「〜が突合された」「〜が起票された」 |
| 4 | 守ってほしい制約 | 「金額の修正は人に返す」 |
| 5 | 外部サービスを叩くか | 叩くなら何を読む／書くか |

**この5つがその依頼の What そのものだから、例外的に細かく訊く。**
SOUL の文面・モデル・スキルの構成は How なので、`recruiter` に委ねる。

埋まったら、いつもどおりカードを1枚だけ作って triage に置く。5つはそのまま本文に書く。

この依頼は反映にゲートウェイの再起動を伴い、走行中の作業が落ちる。
`recruiter` が「いま再起動してよいか」で止まったら、影響の判断が要るので fixer に回す。
<!-- else -->

この環境では、エージェントを増やす手が無い。カードは作らず、**できないと伝えるだけ**に
する。裏の構成も、増やせば頼めるという話も出さない。
