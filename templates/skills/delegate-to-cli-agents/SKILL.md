# CLI エージェントへの委譲

**コードを書く作業は `opencode run` に渡す。**
あなたのターミナルは作業部屋（コンテナ）の中で動いていて、opencode はそこに入っている。

理由は費用と適性の2つ。自分が高性能モデルで直接書くと API 従量課金になる一方、
OpenCode はリポジトリの探索・編集・テスト実行を前提に作られていて、反復作業に向いている。

## 使い分け

| 状況 | やり方 |
|---|---|
| 1行の追記・typo・設定値変更など機械的な作業 | 自分でやる。委譲のほうが高くつく |
| 複数ファイルにまたがる / 探索が要る / テストを回して直す反復 | **`opencode run` に投げる** |
| 調査だけ（コードを変えない） | 自分で `grep` / `read` する |

## 渡し方

対象リポジトリの中から呼ぶ。

```bash
cd /workspace/<repo>
opencode run "<やること。完了条件と触ってよい範囲を明記する>" --auto -m "$OPENCODE_MODEL"
```

**`-m` を省かない。** 省くと opencode が自分でモデルを選び、ツールを実行できないものに
当たると `No endpoints found that support tool use` を返して**何もせずに終わる**。
`$OPENCODE_MODEL` は部屋に用意してある。別のモデルで試したいときだけ、そこに直接書く。

### `--auto` は部屋の中だけ

**この部屋には承認に応えられる人がいない。** 承認ありで走らせると、承認待ちのまま固まり、
誰も答えないままタイムアウトで殺される。だから `--auto` を付ける。

**それが成り立つのは部屋があるからである。** 承認という制御を、隔離が肩代わりしている。

| 走る場所 | 承認 |
|---|---|
| 作業部屋の中（`/workspace`） | `--auto`。**部屋が受ける** |
| ホスト | 承認を残す。**受けるものが無い** |

**その代わり、止める仕組みがプロンプトしか無い。** 範囲と制約を明記する。

### 長い委譲は背面で回す

数分を超えそうなら、前面で待たずに背面へ回してログを読む。

```
terminal("opencode run '…' --auto -m \"$OPENCODE_MODEL\" > /workspace/.hermes/opencode.log 2>&1", background=true)
process_manage(action="poll")                 様子を見る（list / poll / log / wait / kill）
tail -n 50 /workspace/.hermes/opencode.log    進捗を読む
```

`&` / `nohup` / `setsid` は使わない——Hermes が追跡できなくなる。
ログの置き場を `/workspace/.hermes/` にするのは、**clone したリポジトリの外**だからである
（中に置くとコミットに混ざる）。

## プロンプトに必ず含める4点

1. **何を作るか** — 完了条件を検証可能な形で
2. **触ってよい範囲** — ファイル／ディレクトリを明示し、その外は変更しないと明記する
3. **確認方法** — 走らせるテストコマンド
4. **委譲先に任せないこと** — 依存の追加、既存 API の変更、コミット、push

悪い例: 「認証を直して」

良い例:

    src/auth/token.ts の検証ロジックを jose に置き換えよ。
    変更してよいのは src/auth/ の中だけ。npm test が通ることを確認せよ。
    依存の追加とコミットはこちらで行うので、変更だけを残すこと。

## 迷ったときは向こうから知らせてくる

**`--auto` は「聞く」経路を潰している。** 情報が足りなくても opencode は止まらず、
もっともらしい値をでっち上げて「直しました」と報告する——**指示が曖昧なほど起きる。**

そこで部屋の側で約束させてある。**判断に足る情報が無いとき、opencode は何も変更せず
この1行だけを返す。**

```
NEEDS-INPUT: <何が足りないか>
```

**出力の頭にこれがあったら、差分を見る前に止まる。**

```
hermes kanban block --kind needs_input   # 何が足りないかをそのまま書く
```

**自分で埋めないこと。** 埋めた値が正しい保証はどこにも無い。

## 受け取ったものに対する責任

**委譲しても、カードの責任はあなたに残る。** 満たすべきことは4つある。

- **差分そのものを見る。** 委譲先の要約ではなく `git diff` を読む
- **範囲外の変更は戻す**（`git checkout -- <path>`）
- **テストは自分で走らせる。** 「通った」と言われただけでは通っていない
- **コミットと push は自分でやる**（`git push -u origin task/$HERMES_KANBAN_TASK`）

渡したものと差分の要約は `hermes kanban comment` に残す。

的外れな変更が返ってきたら、差分を捨てて自分で書き直すか、`block --kind needs_input`
で相談する。**同じ委譲を3回繰り返す前に止まる。**

続きを頼むときは `--continue` で会話が繋がる。**部屋が生きている間は文脈を貼り直さなくてよい。**

## 委譲先はボードを読めない

**部屋の中に `hermes` は入っていない。** カードの読み書きができるのはあなただけである。
進捗は上のログから拾い、**カードに書くのはあなたが行う。**

同じ理由で、opencode のセッションも部屋と一緒に消える。
**1カード＝1セッション**として扱い、続きは同じ部屋の中で `opencode run` を重ねる。

## リポジトリが持ち込む設定に気をつける

リポジトリに `opencode.json` があると、そのリポジトリの設定が効く。
モデルや MCP サーバを差し込まれると**外部への通信が生える**ので、
見慣れないものがあれば `block --kind needs_input` で報告してから進む。
