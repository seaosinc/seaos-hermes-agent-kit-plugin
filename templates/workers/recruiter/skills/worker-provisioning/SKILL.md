# エージェントを1体つくる

依頼は「請求書のチェックだけやる子が欲しい」のような**役割の話**でカードに書かれて来る。
あなたがやるのは、それを **`templates/workers/<name>/` の一式**に翻訳し、
反映し、**ゲートウェイを再起動して実際に配られる状態にする**ところまでである。
起草だけで渡さない。再起動まで済んでいないものは、できていないのと同じである。

| 作るもの | 何を決めるか | 無いとどうなるか |
|---|---|---|
| `profile.yaml` の `description` | **decomposer がこの子に仕事を振るかどうか** | カードが一生来ない。存在しないのと同じ |
| `SOUL.md` | 何者で、何をやり、何をやらないか | 汎用ワーカーと区別がつかない |
| `skills/<name>/SKILL.md` | 手順（任意） | 毎回やり方を思い出せない |
| `mcp.yaml` | 外部サービスへの口（任意） | その仕事ができない |

**編集するのは常に `templates/workers/` 側である。** `~/.hermes/profiles/` は生成物なので直接触らない。
反映は `seaos-kit update` が行う。

## 0. まず「作らない」を検討する

    seaos-kit worker list

**既存のワーカーの `description` を広げれば済むなら、それが正解である。**
ワーカーが増えるほど decomposer の判別は難しくなり、似た説明が2つ並ぶと配り先が揺れる。

新しく作ってよいのは、次のどれかに当てはまるときだけ:

- **完了条件の形が違う**（例: 既存は「〜が分かっている」、新しい役は「〜が承認された」）
- **専用の手順や判断基準がある**（毎回同じ確認項目を踏む、独自の受け入れ基準がある）
- **専用の外部接続が要る**（その MCP を他の子に持たせたくない）

当てはまらないなら `seaos-kit worker set <既存> --desc "..."` で説明を広げて終わりにする。

**増やせるのは業務別ワーカーだけである。** 固定3役（operator / fixer / broker）は
構成として決まっていて、人と話す窓口は operator ひとつである。
窓口を増やす依頼が来たら、業務別ワーカーとして作れないかを確認する。

## 0.5 直すのか、作るのか

**既存の役を直すほうが多い。** 作る前に、どちらの仕事かを見分ける。

| 頼まれたこと | やること |
|---|---|
| 担当の範囲がずれている | `worker set <役> --desc "..."` |
| モデルが合っていない（速すぎる・賢すぎる） | `worker set <役> --model "..."` |
| 規約に足す・直す | `worker set <役> --soul <ファイル>` |
| 道具が足りない（**fixer から回ってくる典型**） | `worker set <役> --skill <dir>` / `--mcp k=v` |
| 使わなくなった道具を外す | `worker set <役> --rm-skill <名前>` |
| 役そのものが要らない | `worker rm <役>` |

`--skill` は**同名があれば中身ごと差し替える**ので、既存スキルの修正もこれで行う。
直す前に `seaos-kit worker show <役>` で、いま何が載っているかを読む。

**直せるのは業務別ワーカー（`templates/workers/<役>/`）だけである。**
固定役の規約（`templates/profiles/`）、全役に差し込まれる共通ブロック
（`_worker-base.md` / `_worker-impl.md`）、全役が使う共通スキル（`templates/skills/`）は
対象外——**1つ直すと全員の振る舞いが変わる**ので、そこは人が判断する。
頼まれたら「そこは人が決めるところである」と書いて `block --kind needs_input` で止まる。

反映は新設と同じで、`seaos-kit update` を通す（6節）。

## 1. 要件はカード本文から読む

**聞き出しは operator の仕事である。** 足りない情報は `block --kind needs_input` で
求めれば、operator がユーザーに取り次ぐ。

次の5つが本文から読み取れてから、ファイルを書き始める。
半端な `description` を入れた子は、**間違ったカードを引き受けて事故を起こす**。

| | 要る情報 | 例 |
|---|---|---|
| 1 | **名前** | `invoice-check`。英小文字で始まり、英小文字・数字・ハイフンのみ |
| 2 | **典型的な仕事を3つ** | 具体的なカードのタイトルの形で |
| 3 | **完了条件の言い回し** | 「〜が確認された」「〜が起票された」。decomposer の判別材料になる |
| 4 | **守ってほしい制約** | 「金額の修正は人に返す」「請求元への連絡は担当外」 |
| 5 | **外部サービスを叩くか** | 叩くなら、どのサービスの何を読む／書くか |

読み取れないものがあれば、**そのまま止めて聞く**:

    hermes kanban block $TASK_ID --kind needs_input \
    "<name> の完了条件の言い回しが本文から読み取れない。
     A) 『〜が突合された』（推奨。既存ワーカーと重ならない）
     B) 『〜が分かっている』（handler と衝突するので避けたい）
     依頼者に確認してほしい。"

**止めたらその回は終了する。** 回答は次の実行で `show` して読む。

モデルは空のままにする（`MODEL_FAST` が入る）。読解や突合が中心なら賢いモデルを指定する。
重い判断を任せたいと明示されたときだけ `--model` を付ける。

## 2. description を書く（いちばん重要）

decomposer が読むのは**この文だけ**である。SOUL もスキルも読まない。

    <何をする役か>。<やらないこと>。
    例:「<典型カード1>」「<典型カード2>」「<典型カード3>」。
    完了条件が『〜<言い回し>』で終わるタスクはここへ。

守ること:

- **既存ワーカーの description と読み比べる。** 重なっていたら、どちらかに
  「〜は扱わない」を書き足して境界をはっきりさせる
- 抽象語だけで終わらせない。「業務を支援する」では誰も選べない
- 3〜5行。長いほど良いわけではない

## 3. SOUL.md を書く

雛形を出発点にする。**ゼロから書かない。**

    mkdir -p /tmp/recruiter/<name>
    cp <KIT>/templates/workers/_template/SOUL.md /tmp/recruiter/<name>/SOUL.md

**プレースホルダを3つとも残すこと。** 消すと `seaos-kit worker new --soul` が受け付けない:

| 記号 | 意味 | 置き場所 |
|---|---|---|
| `{{NAME}}` | ワーカー名 | **1行目**。`あなたの名前は **{{NAME}}** である。…` で始める |
| `{{WORKER_BASE}}` | 全ワーカー共通の規約が差し込まれる | 本文の後、`{{EXTRA}}` の前。ちょうど1つ |
| `{{EXTRA}}` | `profile.yaml` の `extra` | 末尾 |

**書き換えるのは `{{NAME}}` の行より下、`{{WORKER_BASE}}` より上だけ**である。そこに置くのは:

- `# 役割: {{NAME}}（<一言>）` — 何者か
- `## あなたがやること` — 具体的な作業。動詞で書く
- `## 守る制約` — 1.④で聞いた制約と、その理由
- 判断基準があるなら `## 受け入れ基準` — どうなったら完了と見なすか

**SOUL に書くのは、その役割に固有のことだけである。** 「子エージェントを立てない」
「comment を残す」「`block --kind needs_input` で止まる」
「push まで届かせる」「成果物は $HERMES_KANBAN_WORKSPACE へ置く」は
`{{WORKER_BASE}}` が差し込む。
書き写すと、共通側を直したときに**この子だけ古い規約で動く**。

## 4. 専用スキルを書く（要るときだけ）

**SOUL は「何者か」、スキルは「どうやるか」。** 毎回踏む手順・確認項目・判断表があるなら分ける。
無いなら作らない。中身の薄いスキルは読む手間だけ増やす。

    mkdir -p /tmp/recruiter/<name>/skills/<skill-name>
    # /tmp/recruiter/<name>/skills/<skill-name>/SKILL.md を書く

frontmatter は他のスキルに揃える（`name` / `description` / `version` / `platforms` / `metadata.hermes.tags`）。
`name` はディレクトリ名と一致させること。

**このスキルはそのワーカーだけに入る。** 全プロファイルに配りたい共通規約なら、
ここではなく `templates/skills/` に置く話になるので、勝手に決めず訊く。

## 5. MCP を足す（要るときだけ）

    --mcp <key>='{"command":"npx","args":["-y","@example/mcp-foo"],"env":{"FOO_TOKEN":"${FOO_TOKEN}"}}'

- **無人で成立する認証だけを選ぶ。** ブラウザを開く OAuth（`auth: oauth` のホスト型）は、
  初回も期限切れも人の操作が要る。**誰も見ていない場所で動くので、そのたびに止まる**——
  設定は入っていて `mcp list` は `✓ enabled` と出すのに、呼ぶと
  「no cached tokens found」で落ちる、という形になる（実際に起きた）。
  **トークンで動く stdio 版があるなら、そちらを使う。**
- **鍵は `${VAR}` で参照する。** テンプレートは git に入るので、値を書くとリポジトリへ漏れる
- **使う変数は `--env` で宣言する。** 宣言しないと `env apply` が配らず、
  サーバは起動しても認証されないまま「有効」に見える

      seaos-kit worker set <役> --env FOO_TOKEN="何のトークンか。どこで取るか"

- `.env` への値の記入は**オーナーの作業**である。宣言まで済ませ、
  「この変数を .env に入れてほしい」と報告して止まる
- `enabled` は省略してよい（自動で `true` になる）
- **足したら、実際にツールを1つ呼んで確かめる。** 通ったと言えるのは、
  **その役の実行で読み取りが成功したとき**である。

      hermes -p <役> mcp test <key>              繋がるか（ここまでは必要条件）
      hermes -p <役> chat -q "<ツールを1つ使う指示>"   ← これが通って初めて完了

  `mcp list` の `✓ enabled` は「設定がある」だけ。そして **`mcp test` の成功も
  証明にならない**——起動直後に問い合わせるので、**あとで落ちるサーバは通ってしまう**。
  実際、stdio 版の GitHub MCP は `mcp test` を通ったのに、実行時には
  `MCP stdio subprocess has exited` で毎回落ちていた（HTTP 版へ替えて解決した）
- **無人で動かすなら、子プロセスを持たない形を優先する。** stdio は `npx` の
  子プロセスの寿命に左右される。同じ認証で HTTP のエンドポイントがあるなら、そちらを選ぶ

## 6. 反映する

ここまでの成果物を渡して一気に作る:

    seaos-kit worker new <name> \
      --desc "$(cat /tmp/recruiter/<name>/DESC.txt)" \
      --soul /tmp/recruiter/<name>/SOUL.md \
      --skill /tmp/recruiter/<name>/skills/<skill-name> \
      --mcp <key>='{...}' \
      --json

`--json` の `ok: true` を確認してから次へ。ここまでは `templates/` に書いただけで、まだ動かない。

    seaos-kit update --dry-run    # 何が変わるか読む
    seaos-kit update              # プロファイル作成 → SOUL/model/MCP/skills/description を反映

`update` は最後に `doctor` を回す。**`✗` が1つでも出たら、そこで止まって報告する。**
特に見るのは:

- `--- <name>` の `✓ SOUL.md` `✓ ワーカー共通規約` `✓ 共通ブロック`
- `✓ <name> に description`（無いと decomposer が選べない）
- `✓ model=` と `✓ delegation=`（空だと子が HTTP 400 で即死する）

## 7. 再起動する（**新しい役を作ったときだけ**）

**要るかどうかは、作ったのか直したのかで決まる。**

| やったこと | 再起動 |
|---|---|
| **新しい役を作った**（`worker new`） | **要る。** ゲートウェイが起動時にプロファイル一覧を読むため |
| 既存の役を直した（`worker set` — 説明・SOUL・モデル・スキル・MCP） | **要らない。** 担当はカードごとに新しいプロセスで起こされるので、次のカードから効く |

**要らないなら叩かない。** 再起動は走っている作業を全部落とす——ディスパッチャは
operator のゲートウェイに埋め込まれていて、走行中のワーカーの実行はその子プロセスであり、
**あなた自身の実行も落ちる。** 直しただけで落とすのは、理由のない被害である。

直しただけなら、ここは飛ばして 8 の確認へ進む。

### 7-1. まず自分で数える

    hermes kanban list --status running
    hermes kanban list --status review

### 7-2. 1件でもあれば fixer に判断を仰ぐ

**「たぶん大丈夫」で叩かない。** 走行中のカードがあるなら止まる:

    hermes kanban block $TASK_ID --kind needs_input \
    "<name> の反映は済んだが、有効化にはゲートウェイの再起動が要る。
     いま running のカードが N 件ある（#12 …, #15 …）。再起動すると落ちる。
     A) 走行中が捌けるまで待ち、次の実行で再起動する（推奨。取りこぼしが無い）
     B) いま再起動する（#12 と #15 は落ちるので作り直しが要る）
     決めてほしい。"

止めたらその回は終了する。回答は次の実行で読む。

### 7-3. 空になっていたら再起動する

新しい役を作った場合は、以下の順で進める。

**再起動する前に、ここまでの結果をカードに書く。** あなたの実行も落ちるので、
先に書かないと経緯が消える:

    hermes kanban comment $TASK_ID "<name> の反映と doctor まで完了。
    これからゲートウェイを再起動する。この実行はここで落ちる。
    再開したら 7-4 の確認から始めること。"

そのうえで叩く:

    seaos-kit gateway restart operator --detach

**`--detach` を外さないこと。** あなたの実行はゲートウェイの子プロセスなので、
前面で叩くと再起動の途中で自分が死に、ゲートウェイが停止したまま戻らない。
`--detach` は切り離して走らせるので、あなたが落ちても完走する。

**`hermes gateway restart` を直に叩かないこと。** macOS では定義が再生成されて
`HERMES_PROFILE` が消え、以後カードの発言者が全部 `worker` になって誰が言ったか
追えなくなる。`seaos-kit gateway restart` は OS ごとの作法を吸収する。

### 7-4. 再開したら、上がっていることを確かめる

    seaos-kit doctor

`=== ゲートウェイの HERMES_PROFILE ===` が `✓ operator`、
`=== ディスパッチャ ===` が `✓ kanban dispatcher: …` になっていること。
`✗ ロックを握れていない` なら、もう一度 7-3 をやり直す。

## 8. 動くことを確かめてから完了にする

doctor が通っただけでは「配られる」ことの証明にならない。**テストカードを1枚流す:**

    hermes kanban create "<その子に来るはずの、いちばん典型的な依頼>" --triage

分解の結果 `--assignee <name>` の子カードができれば description は効いている。
別の子に行ったなら description が弱い。`seaos-kit worker set <name> --desc "..."` で直して
`seaos-kit update` からやり直す。

確認が済んだらテストカードは片付ける（`hermes kanban archive <ID>`）。

## 9. 失敗したら戻す

    seaos-kit worker rm <name>          # テンプレートとプロファイルの両方を消す
    seaos-kit worker rm <name> --keep-profile   # プロファイルは残す

進行中のカードを抱えているワーカーは消せない（そう作ってある）。先に片付けること。

## 出す前に確かめること

一覧の左が、実際に踏むと痛い順である。

| 確かめること | 外すとどうなるか |
|---|---|
| 編集したのは `templates/` 側か（`~/.hermes/profiles/` ではないか） | 次の `update` で消える |
| `seaos-kit worker new` を通したか（`hermes profile create` を直に叩いていないか） | `config.yaml` が作られず中途半端になる |
| `description` は具体的か（→ 2.） | 仕事が来ないか、間違った仕事が来る |
| SOUL に共通規約を書き写していないか（→ 3.） | 共通側を直してもこの子だけ古いまま |
| 鍵は `${VAR}` 参照か | リポジトリへ漏れる |
| 走行中・レビュー待ちのカードを数えたか（→ 7-2.） | 走っている作業が黙って落ちる |
| **直しただけなのに再起動していないか**（→ 7.） | 走っている作業を理由なく落とす |
| 新しい役を作ったとき、再起動は `seaos-kit gateway restart` で行ったか（→ 7-3.） | 新しい役に仕事が来ない |
| 再起動に `--detach` を付けたか（→ 7-3.） | 自分が死んで、ゲートウェイが停止したまま戻らない |
| 増やしたのは業務別ワーカーか | 窓口は operator ひとつと決まっている |
| 自分自身のテンプレートに触れていないか | いま何が効いているのか分からなくなる |

自分を直す必要に気づいたら、`block --kind needs_input` で内容を書いて止まる。

## 報告する

作り終えたらカードに残す。次に触る人が再現できる形で:

    hermes kanban comment $TASK_ID "<name> を作成した。
    description: <そのまま貼る>
    SOUL: 役割 / やること / やらないこと を記述
    スキル: <名前 or なし>  MCP: <キー or なし>
    doctor: 全項目 ✓
    再起動: 実施（running 0 件を確認 / fixer の判断: <あれば>）
    テストカード <ID> は <name> に割り当てられた
    オーナーの作業: .env に <VAR> を追加（あれば）"
