## 言葉づかい

**規約の文言はそのまま解釈される。用語がブレると振る舞いもブレる。**
以下の語を使うこと。カッコ内の語は使わない。

| 概念 | 使う語 | 使わない語 |
|---|---|---|
| ボード上の作業単位 | **カード** | タスク、task、チケット、案件 |
| 共有状態そのもの | **ボード** | 看板、kanban（コマンド名としては可） |
| この仕組みを使う人（総称） | **ユーザー** | 人間、利用者、エンドユーザー |
| 制限なく使えるユーザー。アクセス許可を出せる唯一の人 | **オーナー** | 管理者、運用者、owner |
| 期限つきのアクセス許可を持つユーザー | **ゲスト** | 外部ユーザー、来客、ビジター |
| そのカードを頼んだ相手 | **依頼者**（`created_by` に入る） | 起票者、requester |
| 会話してよいという許し | **アクセス許可** | 権限、パーミッション、付与（コマンド名は `guest`） |
| アクセス許可の一覧 | **アクセス許可表**（`reservations.json`） | 予約表、許可リスト |
| 外部 CLI へ実装を出すこと | **委譲** | 委託、丸投げ、外注 |
| カードに担当を割り当てること | **割り当て** | 振る、アサイン |
| コードを書く作業 | **実装** | コーディング、開発、実装作業 |
| 進行を止めること | **block（ブロック）** | 停止、中断、ペンディング |
| カードを畳むこと | **archive** | クローズ、完了扱い、削除 |
| 担当のプロファイル | **担当**（コマンド上は `assignee`） | 担当者、アサイニー |

**アクセス許可は「話してよいか」だけを指す。** 何をしてよいか（どのカードを作れるか、
どのエージェントに回せるか）を表す語ではない。そこは仕組みとして無く、
外れた依頼はオーナーへ上げる（`guest escalate`）。混同すると規約が曖昧になる。

**ユーザーは総称である。** その中にオーナーとゲストがいる。

    ユーザー ─┬─ オーナー   制限なし。アクセス許可を出せる唯一の人
              └─ ゲスト     期限つき。話せるだけ

区別が要る場面では必ずどちらかの語を使い、要らない場面（「ユーザーに報告する」など）は
「ユーザー」でよい。**エージェントと対比するときは「エージェント」の語を使う**
（「ユーザーとエージェント」であって「人間とエージェント」ではない）。

**依頼者はユーザーとは限らない。** `created_by` には `operator` や `auto-decomposer` の
ようなエージェント名も入る（分解で生えたカードの依頼者は decomposer である）。
「そのカードを頼んだ相手」であって「そのカードを頼んだユーザー」ではない。
ゲストの依頼から作るカードでは、**依頼者にそのゲストの Slack ユーザー ID を入れる。**

**委譲と割り当ては別物である。** 委譲は `opencode run` という
外部 CLI に実装を出すこと。割り当ては `--assignee` でカードを役割に渡すこと。
どちらも「振る」と書けてしまうので、必ず区別して書く。

### 役割の名前

**役割名は、固定役と業務別ワーカーの名前だけ。** これ以外の名前を作らない。

- 固定役: `operator`（ユーザーの窓口） / `fixer`（詰まりの解決と完了判定）
<!-- if-role: broker -->
- 固定役: `broker`（外部エージェントとの A2A 連携）
<!-- end-if-role -->
<!-- if-role: developer -->
- 固定役: `developer`（リポジトリの実装）
<!-- end-if-role -->
<!-- if-role: senior-developer -->
- 固定役: `senior-developer`（難度の高いリポジトリの実装）
<!-- end-if-role -->
<!-- if-role: handler -->
- 業務別ワーカー: `handler`（外部サービスの読み書き）
<!-- end-if-role -->
<!-- if-role: recruiter -->
- `recruiter` はエージェントそのものを新設・改修・撤去する
<!-- end-if-role -->
- **ここに無い名前は、この環境では無効か存在しない。** 担当に書かない

**役の名前は人間が覚えるためのもので、仕事の定義は説明文と規約にある。**
名前の連想（「採る」「直す」）で書かず、**何をするか**をそのまま書く。
- 業務別ワーカー: 雛形（`_template`）から生やした、業務ごとの役。**汎用の役は置かない**

**業務別ワーカーは増える。** 実在する名前は `hermes profile list` で確認できる。
役割に言及するときは、**そこにある名前をそのまま使う**（`--assignee` に書く名前も、
本文で呼ぶ名前も同じ語にする）。

「判定担当」「実行役」「審判」のような即席の語をカード本文に書くと、
誰に割り当てるべきか読んだ側が推測するしかなくなる。

### 担当に書けるのは、実在する役の名前だけである

**存在しない名前を書くと、ディスパッチャは黙って飛ばす。** エラーも警告も出ず、
カードは `ready` のまま何時間でも残る。作った側は「開始した」と思い込んだまま、
進捗を聞かれるたびに「まだありません」と答え続けることになる（実際に起きた）。

とくに、**`decomposer` / `auto-decomposer` は役ではない。** カードを作った主体の
名前であって、割り当て先ではない。**分解に載せたいなら、担当を書かずに
`triage` へ置く**——組み込みの decomposer が拾って、担当を決めて promote する。

止まったカードを見つけたら、担当が `hermes profile list` にあるか先に確かめる。

    hermes kanban reassign <id> <実在する役> --reason "<なぜその役か>"

### 状態の名前

ボードの状態は Hermes が定めた語をそのまま使う。言い換えない。

`todo` / `ready` / `running` / `blocked` / `review` / `done` / `archived`

- **`done` は「そのカードが終わった」であって「依頼が完了した」ではない。**
  子カードが `done` でも、依頼全体の達成はルートカードで判定される
- **`archived` は論理削除。** カードもコメントも DB に残っており、`show` すれば読める
