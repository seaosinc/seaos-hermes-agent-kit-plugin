# コミットと版

## 版は2つある。混ぜない

| 版 | どこ | 誰が決めるか |
|---|---|---|
| **プラグインの版** | `plugin.yaml` と `dashboard/manifest.json` の `version` | このスキル（人が決める意味の版） |
| 配布物の版 | 各役の `distribution.yaml` | git から自動（`0.1.<コミット数>+<sha>`。触らない） |

ここで扱うのは**プラグインの版だけ**である。配布物の版は生成器が採るので、手を出さない。

## コミットするとき

**版はまだ動かさない。** 代わりに、そのコミットが版をどう動かすかを本文の最後に1行で書く。

    Version: patch

判定は変更の性質で決める。

| 段 | いつ | 例 |
|---|---|---|
| `major` | 入れている人の手が必要になる | 設定の形が変わる、コマンドの名前が変わる、入れ直しが要る |
| `minor` | できることが増える | 役・スキル・コマンド・画面の機能を足す |
| `patch` | 挙動が同じ場所に戻る | 不具合の修正、文面の直し、テストの追加、内部の整理 |
| `none` | 配るものが変わらない | README だけ、コメントだけ、`.claude/` だけ |

**迷ったら低いほうを選ぶ。** 版は「使う人から見て何が変わったか」であって、
作業量ではない。大きく直しても、外から見て同じなら `patch` である。

コミットの文面は、いつもどおり日本語で「何を、なぜ」を書く。末尾の署名も付ける。

## push するとき

1. **未 push のコミットを読む。**

        git log origin/main..HEAD --format='%s%n%b'

2. **いちばん高い段を採る。** `patch` が3つなら `patch`（3回上げない）。
   `patch` と `minor` が混ざっていれば `minor`。全部 `none` なら版は動かさない。

3. **版を1つだけ上げる。** `plugin.yaml` と `dashboard/manifest.json` の両方を同じ値にする。

        # 例: 1.0.0 で minor なら 1.1.0
        #     1.1.0 で patch なら 1.1.1
        #     1.1.1 で major なら 2.0.0

4. **版だけのコミットを1つ作って push する。**

        git add plugin.yaml dashboard/manifest.json
        git commit -m "版を <新しい版> にする

        <この回に入る変更を1〜3行で>"
        git push origin main

**`Version:` の行が無いコミットは `patch` とみなす。** 書き忘れで版が動かないより、
小さく動くほうが安全である。

## 守ること

- **版を飛ばさない。** 直前の版から1段だけ動かす
- **2つのファイルを必ず揃える。** 片方だけ変わっていると、画面と `hermes plugins list` で
  違う版が出る
- **タグは打たない。** タグはワークフロー（`.github/workflows/release.yml`）が
  コミット数から打つ。こちらの版とは別物である
